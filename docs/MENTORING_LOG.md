# 멘토링 기록

멘토링에서 나온 지적과 그에 대한 **우리 팀의 결정**을 회차별로 남깁니다.
새 회차는 **맨 위에** 추가합니다.

기록하는 이유는 두 가지입니다.

1. 발표 때 "무엇을 지적받았고 어떻게 고쳤는지"를 히스토리로 풀 수 있습니다.
2. 팀원이 이미 고쳐 놓은 것을 다른 사람이 되돌렸을 때 추적할 수 있습니다.

각 항목은 **지적 → 현재 상태 → 결정/조치** 순으로 씁니다.
아직 정하지 못한 것은 **[결정 필요]** 로 표시하고, 정해지면 날짜와 함께 채웁니다.

## 2026-08-25 (2회차)

주제: 아키텍처 검증 · 로그 수집과 경보 설계 · LLM 활용 방향

### 요약

가장 크게 지적받은 것은 **구성도**입니다.
"개발을 처음부터 한 사람조차 자기 아키텍처가 어떻게 구현됐는지 놓치는 경우가 많다.
구성도를 항상 최신 상태로 유지하고 스스로 설명할 수 있어야 한다."

그리고 발표에서는 **계층도와 네트워크 구성도 위에 "어떤 로그를 어디에서 가져왔는지"** 를
반드시 명시해야 하며, **해킹이 어디로 들어와 어디로 나갔는지**를 그림으로 이해시킬 수 있어야 합니다.

### 1. 아키텍처 · 네트워크 구성도

| 지적 | 현재 상태 | 조치 |
| --- | --- | --- |
| 구성도를 최신으로 유지하고 스스로 설명할 수 있어야 함 | LLM 서버 1대 구성만 코드로 존재 | 구성도를 먼저 확정하고, 그 다음에 인프라를 확장한다 |
| Wazuh Agent 를 웹 서버와 Network IDS **양쪽 하위**에 배치 | 구성도 미작성 | 구성도에 반영 |
| Network IDS 위쪽에 "네트워크 로그를 받아들인다" 표시 | 구성도 미작성 | 구성도에 반영 |
| 계층도·구성도에 각 로그의 출처를 매핑 | 미표기 | 구성도에 반영 |
| 엉뚱한 네트워크 장비를 연동하면 안 됨 | — | 구성도 검토 시 확인 |

**목표 구성 (멘토 정리)**

| 구간 | 장비 · 역할 | 수집 로그 |
| --- | --- | --- |
| 외부 | 인터넷 → 방화벽 | — |
| 웹 구간 | 웹 서버 | Access 로그 |
| 웹 구간 | WAF (호스트형 웹방화벽) | 공격 탐지 이벤트 |
| 네트워크 구간 | Network IDS (Suricata) | `eve.json` |
| 수집 | Wazuh Agent | 위 로그를 SIEM 으로 전송 |
| 저장 · 분석 | SIEM (Wazuh) | 정규화 · 상관분석 · 경보 |

**사고 대응 실무 관점** — 해킹 사고가 나면 네트워크 구성도를 가장 먼저 확인하고,
어떤 경로로 들어왔는지 시나리오를 세운 뒤 해당 로그부터 검사합니다.
이 과정에는 구성도를 도메인 지식으로 가진 사람이 반드시 포함됩니다.

**우리 프로젝트에 주는 시사점** — LLM 에게 "우리 구성도는 이렇고 여기서 로그를 수집한다"를
인식시키면, 원래 어디에서 로그를 가져왔어야 하는지 판단하고
**엉뚱한 곳에서 수집 중이면 지적**해 줄 수 있습니다. 증강 블록에 구성도 정보를 넣는 방향을 검토합니다.

### 3. 로그 수집

| 지적 | 현재 상태 | 결정 |
| --- | --- | --- |
| **PCAP 을 SIEM 으로 직접 가져오는 방식은 일반적이지 않다** | `tools/collect_pcap.py` 로 PCAP 을 다룸 | **우리 방식은 이미 맞다.** PCAP 을 SIEM 에 넣는 것이 아니라, PCAP 을 Network IDS 에 재생시켜 `eve.json` 을 **생성**하고 그것을 수집한다. 다만 문서에 오해 소지가 있어 문구를 명확히 함 |
| 수집된 로그에 **payload 가 포함되어 있는지 확인**하고 캡처해 발표본에 삽입 | 미확인 | 확인 후 캡처 (T2) |
| 윈도우 시스템 로그가 보였다 — 실제인가 합성인가 | **합성이다.** `windows_dropper` 는 어댑터 시험용으로 작성한 5줄 | 합성임을 문서와 발표에 명시. 실제 엔드포인트 로그 확보를 과제로 등록 |
| 정규화는 **장비마다 다르게** 소개해야 함 | 어댑터 9종이 이미 장비별로 분리되어 있음 | 웹 서버 로그와 네트워크 로그의 정규화를 **각각 나눠 설명**하도록 문서 보강 (T5) |

### 4. 경보(Alert) 설계 — 미착수

무엇을 경보로 띄울지 아직 정하지 않았습니다. 방향 세 가지:

1. **WAF 이벤트 기반** — SQL Injection 문자열 분석으로 경보
2. **IP 기반** — 특정 출발지 IP 에 대한 경보
3. **상관분석 기반 (핵심)** — WAF 경고 + 웹 서버 200 응답을 함께 본다
   - WAF 에서 공격이 탐지되었고 **웹 서버를 통과했다** → 위험
   - 웹 서버를 통과하지 못했다 → 위험도 하향

**LLM 에게 경보 생성을 맡기는 방향** — 아래 컨텍스트를 주면 Sigma 룰을 만들어 줄 수 있습니다.

- 어떤 로그를 수집하는가
- 어떤 장비를 쓰는가 (Wazuh Agent + SIEM (Wazuh))
- 로그 출처 (웹 서버, Network IDS)
- 어떤 형태로 SIEM 에 전달하는가

### 5. Network IDS 룰 제안 기능의 정당성 — **[결정 필요]**

> "이미 Network IDS 로 탐지가 됐는데, 여기서 또 Suricata 룰을 제안하는 건 이상하지 않나?"

발표에서 반드시 나올 질문입니다. 목적을 **하나로 확정**해야 합니다.

| 선택지 | 목적 | 대가 |
| --- | --- | --- |
| **(A) 미탐(FN) 감소** | NIDS 탐지가 부정확할 수 있으니 정확도를 높인다 | — |
| **(B) 탐지 범위 확대** | 우회 시도를 잡기 위해 scope 를 넓힌다 | **오탐(FP) 이 올라간다** |

→ **[결정 필요]** 목적을 정하고, 정한 목적에 맞춰 프롬프트와 평가 지표를 맞춘다.

### 6. 컨텍스트 윈도우 설계

| 지적 | 현재 상태 | 조치 |
| --- | --- | --- |
| 이벤트 하나만 던지면 안 되고, 관련 로그를 함께 줘야 한다 | 상관분석으로 이미 함께 전달 중 | 유지 |
| 많이 던지면 LLM 이 분석하기 어려워진다 | `AGENT_CONTEXT_MAX_CHARS=24000`, `max_events=50` | 유지하되 절단 사실을 보고하도록 개선 |
| **공격 유형마다 함께 볼 시간대가 다르다** | 전 시나리오 공통 300초 | **공격 유형별 시간 창 정의 필요** (T1) |
| Brute force 는 1~5분 | 미정의 | 프리셋 추가 |
| 공격자가 회피하려 함 (예: 5분에 한 번) | 대응 없음 | 잘 만든 SIEM 은 3일~1주까지 본다. 장기 창 검토 |

시나리오 매니페스트에 `correlation_window_seconds` 가 이미 있어 **시나리오별 조정은 가능**합니다.
공격 유형별 권장값을 정해 프리셋으로 두는 것이 다음 과제입니다.

### 7. 증강(Augmentation) 방향

> "그럼 어떻게 증강을 하고 있는가?" → **사실상 모든 정보는 SIEM 안에 담겨 있다.**
> 증강 소스를 SIEM 기준으로 정리할 것.

현재 우리는 파일(또는 Elasticsearch)에서 읽어 **자체 상관분석 코드**로 증강합니다.
SIEM 이 이미 갖고 있는 정보와 우리가 따로 만드는 정보의 경계를 정리해야 합니다. → **[결정 필요]**

### 8. 검증 에이전트와 비식별

- 파이프라인에 **검증 에이전트**를 둔다.
- 예상 질문: "기밀 정보는 어떻게 처리하나?"
  → **비식별 처리한 뒤 나머지를 전달**하는 방식으로 답변한다.
- 현재 상태: 출력 검증(스키마 강제 · 인용 근거성 검사)은 있으나 **입력 비식별 처리는 없음**. 설계 필요 (T3)

### 9. 실제 분석 시나리오 — Brute Force 예시

웹 방화벽에 brute force 가 다수 유입되었을 때, 출발지 IP 기준으로 이렇게 추적합니다.

1. 웹 서버의 **어떤 페이지**로 들어왔는가
2. 응답 코드가 **404 인가 200 인가**
3. **패킷 사이즈**까지 함께 확인

**판단 순서**

1. 실제로 웹 서버에 들어왔는가
2. 성공했는가 실패했는가
3. 성공 → **즉시 차단** / 실패 → 당장 차단하지 않고 급한 것부터
4. **ID/PW 를 알고 들어온 것인지, 무작위로 때리는 것인지** 실체 확인

→ 이 판단 순서를 그대로 **경보 설계와 프롬프트에 반영**할 수 있습니다.

### 10. 확장성 · 데이터 엔지니어링

> 하루에 약 **100억 건의 이벤트, 5TB 규모의 로그**가 쌓인다.
> 그런 DB 를 설계하고 유실 없이 처리해 탐지해내는 SIEM 을 만들 수 있는가?

- 데이터 전문가가 곧 고급 엔지니어인 영역이며, 보안 분야는 상대적으로 데이터 구조 설계에 약하다.
- 신호가 몰리면 병목이 생기고, 시간이 밀리면 전체 파이프라인에 파동을 미친다.

우리 프로젝트 규모에서 이를 실증하기는 어렵지만,
**설계상 어디가 병목이 되는지는 설명할 수 있어야 합니다.** 발표 대비 항목으로 둡니다.
