# 프로젝트 현황

> 최종 갱신: 2026-08-25
> 프로젝트의 **현재 상태를 한 곳에 모아둔 문서**입니다. 구조가 바뀌거나 단계가 끝날 때마다 갱신합니다.
> 멘토링에서 나온 지적과 그에 대한 결정은 [`MENTORING_LOG.md`](MENTORING_LOG.md) 에 회차별로 남깁니다.

## 1. 한 장 요약

보안관제 현장에서 경보 하나를 판단하려면 방화벽·엔드포인트·네트워크·자산대장·위협정보를 사람이 일일이 돌아다니며 모아야 합니다.
저희는 그 "모으는 일"을 자동화해서 AI에게 한 덩어리로 건네고, AI가 낸 판단을 시스템이 다시 검증한 뒤 사람이 승인하는 구조를 만들고 있습니다.

| 구분 | 내용 |
| --- | --- |
| 프로젝트명 | AI 증강 SIEM (내부 코드명 HAW-KI) |
| **대목표 A** | AI 증강 SIEM 구현 — 로그 수집 → 정규화 → 증강 → AI 분석 → 대응 제안 + 사람 승인 |
| **대목표 B** | 파이프라인 보안성 검증 — 프롬프트 인젝션 등 공격에 이 파이프라인이 견디는지 측정 |
| 차별점 | AI에게 "무엇을 줬는지"를 규격화하고, AI가 "무엇을 근거로 말했는지"를 기계적으로 검증 |
| 현재 상태 | 대목표 A의 전 단계가 실제 GPU 모델로 끝까지 동작 확인 완료 (2026-08-24) |

> **핵심 한 문장** — AWS GPU 위의 GPT-OSS 20B가 저희가 조립한 4블록 증거 번들을 받아 실제 사건 판단을 생성했고,
> 그 판단이 인용한 이벤트 ID 전부가 실제 증거에 존재하는지 시스템이 대조해 통과했습니다.
> 데모 데이터가 아니라 실제 모델 추론 결과입니다.

## 2. 파이프라인 — 5단계

| 단계 | 하는 일 | 구현 상태 |
| --- | --- | --- |
| ① 로그 생성 | 엔드포인트(Sysmon) · 호스트 IDS(Wazuh) · Network IDS (Suricata) · 웹 서버(nginx) · WAF(ModSecurity) | 시나리오 3종 |
| ② 수집 · 정규화 | 서로 다른 형식을 ECS 필드로 통일. 원본은 `event.original` 에 보존 | 완료 |
| ③ **증강 (핵심)** | 규칙 기반 상관분석으로 관련 이벤트를 묶고, 4블록 증거 번들로 조립 | 완료 |
| ④ AI 분석 | 번들을 프롬프트로 만들어 LLM에 전달, 구조화된 판단을 수신 | 완료 (실제 GPU 모델) |
| ⑤ 대응 제안 + 승인 | 모든 조치를 승인 필수로 제안. 감사 기록에 남김 | 제안 생성 완료 / 승인 흐름 점검 필요 |

### ③ 증강 — 4블록 증거 번들

스키마 이름은 `hawki.siem.evidence-bundle/v1` 이며 네 개 블록으로 고정되어 있습니다.

| 블록 | 담는 것 | 설계 원칙 |
| --- | --- | --- |
| `security_alerts` | 탐지된 경보. 첫 번째는 트리거 역할 | 탐지는 생산자의 의견이지 사실이 아니다 |
| `security_events` | 상관된 원본 텔레메트리 (`event.original` 보존) | 원본을 요약하거나 변형하지 않는다 |
| `assets` | 관측된 호스트의 자산 정보 | 업무중요도·노출범위·데이터등급은 영향도 판단용이지 가능성 판단용이 아니다 |
| `threat_intelligence` | 관측값에 대한 지표 정보 | 매칭은 의심을 높일 뿐 침해를 증명하지 않고, 매칭 없음이 안전을 뜻하지 않는다 |

### 상관분석 — 규칙 기반, 결정적

AI가 아니라 코드가 점수를 매깁니다. 같은 값이 들어오면 항상 같은 결과가 나와야 재현 가능한 실험이 되기 때문입니다.

- 동일 `flow_id` +7 · 동일 호스트 +5 · 트리거와 같은 출발지 IP +4 · 같은 목적지 IP +4 · 같은 사용자 +2 · 같은 응용 프로토콜 +1 · 시간 근접 +1
- 합계 2점 이상, 300초 창 안의 이벤트만 묶음
- 화면에 `within 8s` / `same host` / `same user` 처럼 **묶은 근거를 그대로 표시**

## 3. 검증 장치 — 차별점

생성형 AI를 보안 업무에 쓸 때 가장 먼저 나오는 질문은 "그 말을 믿어도 되느냐"입니다.
세 가지 기계적 장치로 답합니다.

1. **출력 스키마 강제** — 사건 판단은 11개 필수 항목을 반드시 채워야 합니다. 빠진 항목은 이름과 함께 화면에 표시되고 1회 보정 요청이 나갑니다.
2. **인용 근거성 검사** — 모델이 인용한 이벤트 ID를 실제 번들과 대조합니다. 번들에 없는 ID를 인용하면 **조용히 고치지 않고** "근거 없는 인용"으로 드러냅니다.
3. **모순 증거 명시** — 모순 증거가 비어 있으면 그 사실을 문구로 붙입니다. 모순을 찾아보지 않은 모델과 정말 모순이 없는 사건이 화면에서 똑같아 보이면 안 되기 때문입니다.

### 설계에 박아둔 원칙

- **원본 보존 · 의미역 보존 · 손실 보고** — 로그를 요약하지 않고, 필드의 의미를 바꾸지 않으며, 버린 것이 있으면 보고한다
- **매칭 없음 ≠ 안전** — 위협정보에 없다는 것은 정보가 없다는 뜻이지 안전하다는 뜻이 아니다
- **시간 근접 ≠ 인과** — 붙어서 일어났다고 원인과 결과가 아니다
- **순환 논증 금지** — 탐지 결과를 근거로 탐지가 옳다고 말하지 않는다
- **모든 조치는 승인 필수** — AI는 제안만 하고 실행은 사람이 승인한다

> 실제 실행에서 이 원칙들이 지켜지는 것을 확인했습니다. 증거가 부족했던 초기 실행에서 모델은
> "구체적 증거가 없으므로 신뢰도·심각도·ATT&CK 기법을 부여할 수 없다"고 판단을 **거부**했습니다. 지어내지 않았습니다.

## 4. 시나리오 — 출처가 다릅니다

| 시나리오 | 로그 출처 | 위협정보 매칭 |
| --- | --- | --- |
| `mta_001` | **실제 캡처** — malware-traffic-analysis.net 자료를 Network IDS (Suricata) + ET Open 으로 재생 | 0건 (사전에 해당 IP 없음) |
| `windows_dropper` | 손으로 작성한 Sysmon · Wazuh 이벤트 | 3건 (직접 넣은 값) |
| `web_path_traversal` | 손으로 작성한 nginx · ModSecurity · Suricata · Wazuh | 직접 넣은 값 |

`mta_001` 은 실제 감염 PC(10.2.28.88)가 진짜 C2(45.131.214.85)로 NetSupport RAT 체크인을 하는 트래픽입니다.
443 포트인데 TLS가 아니라 평문 HTTP를 쓰는 실제 회피 수법이 그대로 담겨 있습니다.

## 5. 경보(Alert) 설계 — 미착수

무엇을 경보로 띄울지 아직 정하지 않았습니다. 지금은 시나리오 파일에 이미 들어 있는
탐지 결과를 트리거로 쓰고 있어, **우리가 정의한 경보는 없습니다.**

### 설계 방향 세 가지

| 방향 | 내용 | 비고 |
| --- | --- | --- |
| WAF 이벤트 기반 | SQL Injection 등을 문자열 분석으로 탐지 | 단순하지만 오탐이 많음 |
| IP 기반 | 특정 출발지 IP 에 대한 경보 | 위협정보 연동과 맞물림 |
| **상관분석 기반 (핵심)** | WAF 경고 + 웹 서버 응답을 함께 본다 | 우리 파이프라인의 강점이 그대로 쓰임 |

**상관분석 기반이 핵심인 이유**

- WAF 에서 공격이 탐지되었고 **웹 서버가 200 을 돌려줬다** → 통과했다는 뜻 → **위험**
- WAF 에서 탐지되었지만 웹 서버가 **404 · 403** → 통과하지 못했다 → **위험도 하향**

같은 공격 시도라도 "막혔는가 통과했는가"에 따라 대응 우선순위가 완전히 달라집니다.
단일 장비의 경보만 보면 이 구분을 할 수 없고, **두 장비의 로그를 묶어야만** 판단할 수 있습니다.
저희가 만든 상관분석이 실제로 필요한 이유가 여기에 있습니다.

### 실무 판단 순서 (Brute Force 예시)

웹 방화벽에 brute force 가 다수 유입되었을 때, 출발지 IP 기준으로 이렇게 추적합니다.

1. 웹 서버의 **어떤 페이지**로 들어왔는가
2. 응답 코드가 **404 인가 200 인가**
3. **패킷 사이즈**까지 함께 확인

그리고 이 순서로 판단합니다.

1. 실제로 웹 서버에 들어왔는가
2. 성공했는가 실패했는가
3. 성공 → **즉시 차단** / 실패 → 당장 차단하지 않고 급한 것부터 처리
4. **ID/PW 를 알고 들어온 것인지, 무작위로 때리는 것인지** 실체 확인

이 판단 순서를 경보 정의와 프롬프트에 그대로 반영하는 것이 다음 과제입니다.

### 컨텍스트 윈도우 — 공격 유형마다 다르다

이벤트 하나만 모델에 던지면 판단할 수 없고, 그렇다고 많이 던지면 모델이 분석하기 어려워집니다.
**함께 볼 시간 범위는 공격 유형마다 달라야 합니다.**

| 공격 유형 | 함께 볼 범위 | 근거 |
| --- | --- | --- |
| Brute force | 1~5분 | 짧은 시간에 반복되는 시도 |
| 회피형 (예: 5분에 한 번) | 3일 ~ 1주 | 공격자가 짧은 창을 피해 간다. 잘 만들어진 SIEM 은 이 범위까지 본다 |
| 현재 우리 기본값 | **300초 (전 시나리오 공통)** | 공격 유형별 구분 없음 |

시나리오 매니페스트에 `correlation_window_seconds` 가 이미 있어 **시나리오별 조정은 가능**합니다.
공격 유형별 권장값을 프리셋으로 정의하는 것이 남은 일입니다.

### LLM 에게 경보 생성을 맡기는 방향

다음 컨텍스트를 주면 Sigma 룰을 생성할 수 있습니다.

- 어떤 로그를 수집하는가
- 어떤 장비를 쓰는가 — Wazuh Agent + SIEM (Wazuh)
- 로그 출처 — 웹 서버, Network IDS (Suricata)
- 어떤 형태로 SIEM 에 전달하는가

## 7. 현재 한계 — 솔직하게

| 한계 | 현재 상태 | 언제까지 |
| --- | --- | --- |
| **위협정보가 합성 데이터** | 자체 제작 지표 6건. 실제 피드 미연동. 실제 캡처(`mta_001`)에는 매칭 0건 | 7주차 전 (최우선) |
| 시나리오 3종뿐 | 표본이 적음 | 7주차 |
| 모순 증거 사례 없음 | 모순을 찾도록 설계된 시나리오가 없음 | 8주차 |
| 판단 재현성 미측정 | 같은 증거에 심각도가 medium/critical 로 갈리는 것을 관찰 | 8주차 |
| 승인 흐름 미완주 | 제안은 생성되나 승인·감사 기록까지 끝까지 돌려보지 않음 | 다음 주 |
| 대목표 B 미착수 | garak · promptfoo · Guardrail 비교 실험 준비 단계 | 9주차부터 |
| Python 3.10 호환성 | `models.py` 날짜 파싱이 3.10에서 실패 (Ubuntu 22.04 기준) | 다음 주 |
| 상관 이벤트 절단이 보고되지 않음 | `max_events=50` 으로 잘리는데 몇 건이 빠졌는지 알리지 않음 | 다음 주 |
| **네트워크 구성도 없음** | 어떤 장비에서 어떤 로그를 가져오는지 그림으로 설명할 수 없음 | **이번 주 (최우선)** |
| 우리가 정의한 경보가 없음 | 시나리오에 들어 있는 탐지 결과를 그대로 트리거로 사용 | 이번 주 |
| 컨텍스트 윈도우가 공격 유형과 무관 | 전 시나리오 공통 300초 | 다음 주 |
| 입력 비식별 처리 없음 | 출력 검증만 있고, 모델에 보내기 전 민감정보 처리 단계가 없음 | 8주차 |
| payload 포함 여부 미확인 | 수집된 로그에 실제 페이로드가 들어 있는지 확인하지 않음 | 이번 주 |

**한 줄로 말하면** — 실제 캡처에는 위협정보가 하나도 안 붙고, 위협정보가 붙는 사건은 우리가 직접 만든 것뿐입니다.
즉 지금은 "우리가 심어둔 답을 우리가 찾아낸" 상태입니다.

## 8. 지금 결정해야 할 것

발표에서 반드시 질문받을 항목입니다. 팀에서 답을 하나로 정해야 합니다.

### ① Network IDS 룰 제안 기능의 목적

> "이미 Network IDS 로 탐지가 됐는데, 여기서 또 Suricata 룰을 제안하는 건 이상하지 않나?"

| 선택지 | 목적 | 대가 |
| --- | --- | --- |
| **(A) 미탐(FN) 감소** | NIDS 탐지가 부정확할 수 있으니 정확도를 높인다 | — |
| **(B) 탐지 범위 확대** | 우회 시도를 잡기 위해 scope 를 넓힌다 | **오탐(FP) 이 올라간다** |

**하나를 고르면 프롬프트와 평가 지표가 함께 정해집니다.**
(A) 를 고르면 "놓친 것을 잡았는가"를 재고, (B) 를 고르면 "얼마나 넓혔고 오탐이 얼마나 늘었는가"를 잽니다.
지금처럼 목적이 없으면 어느 쪽으로도 측정할 수 없습니다.

### ② 증강의 경계 — SIEM 이 이미 가진 것과 우리가 만드는 것

> "사실상 모든 정보는 SIEM 안에 담겨 있다. 증강 소스를 SIEM 기준으로 정리할 것."

현재 우리는 파일에서 읽어 **자체 상관분석 코드**로 증강합니다.
SIEM 이 이미 제공하는 것과 우리가 추가로 만드는 것의 경계를 정리해야,
"왜 SIEM 위에 또 만들었는가"에 답할 수 있습니다.

### ③ 구성도 정보를 증강 블록에 넣을 것인가

LLM 에게 "우리 구성도는 이렇고 여기서 로그를 수집한다"를 인식시키면,
**엉뚱한 곳에서 로그를 수집 중일 때 지적**해 줄 수 있습니다.
4블록 번들에 다섯 번째 블록(구성 정보)을 더할지, 시스템 프롬프트에 넣을지 정해야 합니다.

## 9. 앞으로의 방향

### 대목표 A — 파이프라인 완성

| 과제 | 무엇을 하는가 | 완료 기준 |
| --- | --- | --- |
| 실제 위협정보 연동 | abuse.ch URLhaus/ThreatFox 를 주기적으로 받아 지표 블록에 주입 | 합성 피드 없이 실제 지표로 매칭 발생 |
| 시나리오 확대 | 공개 데이터셋 기반 공격 재현. 최소 8종 | 네트워크·웹·엔드포인트 유형이 고루 포함 |
| 승인 흐름 완주 | 제안 → 승인 대기 → 승인/거부 → 감사 기록까지 1회 관통 | 감사 기록에 승인자와 시각이 남음 |
| 실측 비교 | 증강 있음/없음 조건에서 판단 품질 비교 | `comparison.md` 에 실제 모델 기준 수치 |
| Suricata 센서 연동 | PCAP 재생으로 네트워크 경보를 실제로 생성 | 센서 산출 경보로 파이프라인 구동 |

### 대목표 B — 파이프라인 보안성 검증

증강 파이프라인은 **로그 내용을 AI에게 그대로 전달**합니다.
즉 공격자가 로그에 남길 수 있는 문자열이 곧 AI에게 가는 입력이 됩니다.

| 과제 | 무엇을 하는가 | 완료 기준 |
| --- | --- | --- |
| 공격 데이터셋 확보 | BIPIA (원 출처 `github.com/microsoft/BIPIA`, arXiv 2312.14197), OWASP Prompt Injection Benchmark V2 | 재배포본이 아닌 원 출처 인용 |
| 자동 점검 도구 적용 | garak(취약점 스캔) · promptfoo(레드팀 시나리오) | 실행 로그와 리포트 산출 |
| Guardrail 전후 비교 | 방어 장치 적용 전후의 공격 성공률 측정 | 동일 조건 수치 비교표 |
| 로그 기반 인젝션 실험 | 실제 웹 로그의 User-Agent·URI 에 지시문을 심어 통과 여부 확인 | 구조 고유의 취약점 유무 판정 |
| 모순 증거 유도 실험 | 자산 정보와 위협정보가 충돌하는 시나리오 설계 | 모델이 모순을 찾아내는지 측정 |

> "AI로 보안을 한다"는 팀은 많지만, **"그 AI 파이프라인 자체가 안전한가"** 를 측정하는 팀은 드뭅니다.
> 프로젝트의 독자성은 여기에 있습니다.

### 트랙별 첫 주 과제 (2026-08-25 멘토링 반영)

**T1 파이프라인 · 백엔드**
- 공격 유형별 상관분석 시간 창 프리셋 정의 (brute force 1~5분 / 장기 3일~1주)
- `max_events=50` 절단 사실을 번들에 보고하도록 수정
- 승인 흐름을 끝까지 1회 관통하고 감사 기록 확인
- `models.py` 의 Python 3.10 날짜 파싱 오류 수정 (AWS 배포 시 실패 원인)
- `tests/test_alert_analysis.py` 실패 2건 수정

**T2 데이터 · 시나리오**
- **수집 로그에 payload 가 포함되어 있는지 확인하고 캡처** (발표본 삽입용)
- abuse.ch URLhaus/ThreatFox 수집 스크립트 작성 및 지표 블록 주입
- 실제 엔드포인트 로그 확보 (현재 Sysmon 은 시험용 5줄)
- 신규 시나리오 2종 추가 (네트워크 계열 1, 웹 계열 1)

**T3 보안성 검증**
- **검증 에이전트의 비식별 처리 로직 설계** — 모델에 보내기 전 민감정보 처리
- garak · promptfoo 로컬 설치 및 예제 1회 실행
- BIPIA 원 저장소에서 데이터 확보, 라이선스 확인
- 실험 설계서 초안 — 무엇을 성공/실패로 볼 것인지 정의

**T4 인프라 · 운영**
- **네트워크 구성도 확정** — 데이터 흐름, 네트워크 경계, 접근 통제, 각 서버 설치 목록, 공격자 위치
- 구성도대로 AWS 인프라 확장 (기존 코드 위에 추가, **6주차 내 완료 목표**)
- 서버 그룹별 전원 스위치 확장 (`lab_running` 을 그룹 단위로)
- `main` 브랜치 보호 설정 / AWS 비용 주간 보고 양식

**T5 문서 · 발표**
- 계층도 · 구성도에 **각 로그의 출처 매핑** 표기
- 웹 서버 로그 / 네트워크 로그 **정규화 방식을 각각 분리해** 정리
- **Network IDS 룰 오류 → 수정 이력 문서화** (발표용 히스토리)
- 설계서 수정 블록을 HWP 양식에 반영
- 로그 전송 에이전트 명칭 재확인
